# Add a migration

The domain model is canonical; the ORM follows it; the migration follows the ORM.
Work in that order, and never let autogenerate output ship unreviewed.

## 1. Change the models, domain first

1. Update the Pydantic domain model in `backend/src/problemfinder/domain/`.
2. Mirror the change in the ORM row in `persistence/orm/` and the translation in
   `persistence/mapping.py`.
3. Run the parity gate immediately: `cd backend && uv run pytest tests/persistence -q`.
   It fails until domain fields and columns line up again, including nullability.

## 2. Generate and review

```bash
make up                                        # Postgres must be running
cd backend && uv run pf db revision -m "add <thing>"
```

Open the new file in `persistence/migrations/versions/` and review every operation:

- Autogenerate misses server defaults, some index changes, and enum value changes.
- Constraint names must come from the naming convention (they will, if the ORM
  declared them); never hand-name constraints.
- **Any `drop_column`, `drop_table`, or type change that loses data requires explicit
  user confirmation before proceeding. Stop and ask.**

## 3. Apply and verify

```bash
make migrate                                   # alembic upgrade head
cd backend && uv run pytest -q                 # full suite against the new schema
```

If the API contract changed (domain model is API-visible), also run `make openapi`
and commit the regenerated `openapi.json` and `schema.d.ts`.

## 4. Downgrade honesty

Autogenerated downgrades that would destroy data should either be corrected to a real
inverse or replaced with `raise NotImplementedError("destructive downgrade")` plus a
comment. Never leave a silently lossy downgrade in place.
